# LogSentry

![tests](https://github.com/parkbeomjun664/logsentry/actions/workflows/test.yml/badge.svg)

표준 웹서버 접근 로그를 읽어 **침입 시도를 탐지·기록**하는 범용 도구.
대상 앱의 코드를 고치지 않고, **어느 프로젝트든 로그만 있으면** 붙는다. 의존성 0(파이썬 표준 라이브러리만).

> A lightweight, dependency-free intrusion detector that reads standard web access logs
> (nginx/apache/JSON) and flags scanning, brute-force, and slow/distributed attacks — no app changes.

---

## 왜 만들었나

AI 기반 자동 공격은 로그인 화면만이 아니라 **API·없는 주소를 빠르게·넓게·느리게** 쑤신다.
대부분의 서버는 이미 모든 요청을 접근 로그에 남긴다. LogSentry 는 **그 로그만 읽어**, 코드 수정 없이
공격 징후를 찾아 경보하고 기록한다.

INFOLINK MES 보안 과제에서 만든 침입 탐지 규칙(계정 잠금·경로 탐색·IP 상관분석 등)을,
특정 DB·프레임워크에 묶이지 않도록 **로그 기반·프로젝트 독립**으로 이식한 결과물이다.

## 핵심 특징

- **코드 무수정** — 대상 앱을 전혀 건드리지 않는다. 로그 파일만 가리키면 된다.
- **범용** — nginx/apache combined, JSON 접근 로그, **Caddy 접근 로그(JSON)** 지원(자동 감지). 양식은 파서(어댑터)만 추가하면 늘어난다.
- **의존성 0** — 파이썬 표준 라이브러리만. 어디서나 실행.
- **자동 감시** — `--watch` 로 주기 재검사, 새 경보만 알림.
- **기록** — `--alert-log` 로 경보를 ASCII 구조(key=value)로 남겨 어떤 인코딩·도구에서도 안 깨지고 파싱 가능.
- **알림** — `--webhook` 으로 새 경보를 슬랙/디스코드/범용 HTTP 로 전송(실패해도 감시는 계속).
- **실시간 상황판** — `--dashboard` 로 웹 화면에서 침투를 실시간 타임라인으로(줄 클릭 시 상세·규칙 기반 대응 추천, 다크/라이트). 순수 표준 라이브러리만.
- **종류별 보기 · 검색 · Top 패널** — 유형별 탭, IP·경로·도구 검색창, "가장 많이 공격한 IP/노린 경로" Top 패널(클릭 시 그 값으로 검색), 자동 새로고침 일시정지 토글.
- **IP 차단(선택적 조치)** — 상황판에서 해당 침투 IP를 바로 차단(Windows 방화벽 inbound). **영구·임시(N분 자동 해제)·대역(/24)** 선택. 안전장치: IP 형식 엄격 검증(명령어 주입 차단)·자기자신/링크로컬 거부·사설 경고·**한 번 더 확인(심각한 건 2단계)**·**실행 취소(되돌리기)**·모든 시도 감사기록(DB). 실제 차단은 관리자 권한 필요(없으면 안내만).
- **그 외 조치** — **증거 저장**(그 IP 침투 기록을 파일로, 보고·신고용) · **오탐 처리(신뢰 IP)**(이건 공격 아님 → 이후 세지도 보이지도 않음, 되돌리기 가능).
- **침투 흔적 DB** — `--db`(SQLite·파이썬 내장)에 흔적을 영구 저장(재시작·로그 교체에도 보존), `--show-db` 로 터미널 조회. 차단 내역·감사기록도 같은 DB에.
- **설정 파일** — `logsentry.json` 으로 탐침경로·도구지문·신뢰IP·문턱·웹훅을 코드 수정 없이 회사별로 조정. 없으면 기본값.
- **오탐 관리** — 정상 트래픽/소음(favicon 등)·신뢰 IP 제외, 확실한 것만 경보·애매한 것은 관찰.

## 설치 / 실행

파이썬 3.11+ 만 있으면 된다. 설치 불필요.

```bash
# 한 번 검사
python logsentry.py access.log

# 자동 감시(60초마다, 새 경보만) + 파일 기록
python logsentry.py /var/log/nginx/access.log --watch 60 --alert-log alerts.txt

# 실시간 상황판(웹 화면) — 침투 타임라인 + 흔적 DB 저장. http://127.0.0.1:8787
python logsentry.py /var/log/nginx/access.log --dashboard 8787

# 쌓인 침투 흔적 DB 조회(최근 30건)
python logsentry.py --show-db
```

## 테스트

탐지 규칙이 깨지지 않았는지 자동으로 확인한다(표준 라이브러리 unittest, 의존성 0).

```bash
python -m unittest -v
```

스캐너·로그인 무차별·느린/복합/분산 공격은 경보로 잡고 정상 사용자·favicon 소음은 잡지 않는지,
또 설정 적용·신뢰 IP 제외·웹훅 전송·계정 차원(스프레이·집중·단순 무차별)·비표준 상태코드·상황판 집계·흔적 DB 저장·IP 차단 안전장치(형식검증·자기자신 거부·감사기록)·대역 차단·증거 저장·신뢰(오탐) 처리·Top 패널 집계까지 — 모두 **61가지 상황**을 검사한다. 상황판 화면 JS 는 `node --check` 로 문법까지 검증한다.
결과(경보 여부)뿐 아니라 셈(없는 주소 횟수 등)까지 확인해, 다른 점수에 가려
고장이 조용히 지나가지 않게 했다.

## 탐지 규칙

| 규칙 | 내용 |
|---|---|
| P1 경로 탐색 | 한 IP 가 없는 주소(404)를 여러 번 |
| P2 인증 두드림 | 한 IP 가 인증 실패(401·403·423…)를 여러 번. 423=계정잠금은 무차별의 결정적 증거. 설정으로 상태코드 조정 |
| P3 과속 | 한 IP 가 짧은 시간(창) 안에 많은 요청 |
| P4 도구 지문 | User-Agent 가 curl/python/sqlmap/nmap 등 |
| P5 IP 종합 | 위 신호를 IP 로 합산·점수화 → 저속·복합 공격까지 |
| P6 분산(v2) | 짧은 시간창에 여러 IP 가 같은 공격(인증실패·404). IP 별로는 조용한 분산 무차별·스캔을 서버 전체 관점에서 |

> 계정 단위(비밀번호 스프레이·계정 잠금)는 접근 로그에 계정 정보가 없어, 앱 연동 단계(v2)에서 추가.

## 설계

```
 로그 한 줄 ─▶ [ 파서(어댑터) ] ─▶ 공통 이벤트 ─▶ [ 탐지 엔진 ] ─▶ [ 보여주기 ]
                nginx / json          {ip·경로·상태·지문}   P1~P5 점수화     화면(한글) / 파일(ASCII)
```

- **파서(입구)만 양식을 탄다.** JSON·apache 등은 파서 하나 추가 → 탐지 엔진은 그대로 재사용(어댑터 패턴).
- **자료와 보여주기를 분리.** 탐지 엔진은 사실(dict)만 만들고, 화면용·파일용 포맷은 바깥에서.

## 옵션

```
--watch N           N초마다 자동 재검사(새 경보만)
--alert-log FILE    경보를 파일에 이어 기록(ASCII)
--webhook URL       새 경보를 웹훅으로 전송(슬랙/디스코드/범용 HTTP)
--config FILE       설정 파일(JSON) — 탐침경로·도구지문·신뢰IP·문턱·웹훅 덮어씀(기본 logsentry.json)
--window N          과속·창 크기(기본 60초)
--probe-threshold   경로 탐색 경보 문턱(기본 5)
--auth-threshold    인증 두드림 경보 문턱(기본 5)
--rate-threshold    과속 문턱(기본 20req/창)
--score-threshold   종합 점수 경보 문턱(기본 6)
--dist-threshold    분산 경보 문턱 — 한 시간창 안 서로 다른 IP 수(기본 5)
--dashboard PORT    실시간 상황판(웹 화면)을 이 포트로 띄움(예: --dashboard 8787)
--host ADDR         상황판 바인드 주소(기본 127.0.0.1=이 PC만; 사내망 공유는 0.0.0.0)
--scan-interval N   상황판이 로그를 다시 읽는 주기(초, 기본 5)
--db FILE           침투 흔적 SQLite DB(기본 logsentry.db; 빈 값이면 끔)
--show-db [N]       쌓인 DB에서 최근 N건(기본 30)을 표로 보여주고 종료
```

## 설정 파일 예시 (`logsentry.json`)

실제 운영(Next.js 웹 + Spring API, 앞단 Caddy)에 붙여 하루 관찰한 뒤 정리한 설정이다.

```json
{
  "skip_extra": ["/_next/static/", "/_next/image", "/icon.svg", "/actuator/health"],
  "trusted_ips": ["::1", "127.0.0.1"],
  "auth_paths": ["/api/v1/auth/login"],
  "auth_statuses": [401, 403, 423, 429],
  "suspicious_headers": ["Next-Action"],
  "thresholds": {"rate": 120}
}
```

| 키 | 뜻 |
|---|---|
| `skip` / `skip_extra` | 세지 않을 정상 소음 경로(앞부분 일치). 화면 하나에 정적 파일 수십 개가 따라오면 과속으로 오탐하므로 뺀다. `skip` 은 기본 목록을 **덮어쓰고**, `skip_extra` 는 기본 목록에 **덧붙인다**(`probe_paths_extra`·`tool_ua_extra` 도 같은 방식) |
| `trusted_ips` | 경보에서 뺄 주소. **대역(CIDR)도 가능**(`"192.168.10.0/24"`). ⚠ 통신사 LTE IP 는 여러 사람이 같이 쓰므로 넣지 말 것 |
| `auth_paths` | 지정하면 **이 경로의 401/403/423 만 로그인 실패**로 센다. 다른 경로의 401 은 "권한 밖 경로(정찰)"로 분류 — 로그인 안 한 요청에 전부 401 을 주는 API 에서 스캐너가 무차별 대입으로 잘못 보이는 것을 막는다 |
| `auth_statuses` | 로그인 실패로 볼 상태코드. 로그인 IP 차단이 걸렸을 때 429 를 주는 서버면 추가(`auth_paths` 를 지정했으면 다른 경로의 429 와 섞이지 않음) |
| `suspicious_headers` | 한 번만 와도 위험으로 볼 요청 헤더(Caddy 로그에서 읽음). 기본 `Next-Action` — Next.js 서버 액션 헤더로, React2Shell(CVE-2025-55182) 류 원격 코드 실행 공격에 쓰인다. **서버 액션을 실제로 쓰는 앱이면 `[]` 로 비울 것** |
| `thresholds` | 문턱 덮어쓰기(`window`·`probe`·`auth`·`rate`·`score`·`dist_ip`) |

표준이 아닌 HTTP 메서드(예: nmap 서비스 탐지의 `EKDW`·`XYFK`)와 Nmap 고정 탐침(`/nice ports,/Trinity.txt.bak`)도 기본으로 잡는다.

## 미들웨어 어댑터 (v2 · 계정 차원)

접근 로그엔 **'어느 계정을 노렸나'가 없다.** 그래서 비밀번호 스프레이(한 공격자가 여러 계정에 흔한 비번을 1회씩 — 계정 잠금도 안 걸린다)는 로그 분석만으론 안 보인다. 앱에 `LoginTracker` 를 **드롭인**하면 계정 차원으로 잡는다 — 대상 앱은 `record`/`check` 두 줄만 꽂으면 된다.

- **비밀번호 스프레이** — 한 IP 가 시간창 안에 서로 다른 계정 여럿에 실패
- **계정 집중 공격** — 한 계정에 서로 다른 IP 여럿이 실패(분산 브루트포스)
- **단순 무차별** — 한 (IP, 계정) 조합이 반복 실패(아이디 그대로 비밀번호만 바꿔 여러 번 — 가장 전형적인 로그인 공격)

```python
from logsentry import LoginTracker
tracker = LoginTracker(window=300, spray_threshold=5, account_threshold=5)

# 로그인 처리 직후 (예: FastAPI)
tracker.record(ip=request.client.host, account=login_id, success=ok)

# 주기적으로(백그라운드 작업 등)
for hit in tracker.check():
    notify(hit)   # 슬랙/메일 등
```

## 로드맵

- **v0** 접근 로그 → P1~P5 탐지 ✅
- **v1** nginx·apache·JSON 파서 · 파일 기록 · 자동 감시 · 설정 파일 · 웹훅 알림 ✅
- **v2** 서버 전체 레벨 분산 탐지(분산 무차별·분산 스캔) ✅ · 드롭인 미들웨어 어댑터(계정 스프레이·집중·단순 무차별) ✅
  - AI 엔드포인트 가드(프롬프트 인젝션)는 로그 분석이 아닌 **앱 로직 영역** — 실적용(ShotTrace)에서 출력-데이터 교차검증으로 구현
- **v3** 실시간 상황판(웹·순수 표준 라이브러리) · 종류별 보기 · 침투 흔적 DB(SQLite 내장) · 규칙 기반 대응 추천 · **원클릭 IP 차단(상황판 → Windows 방화벽, 안전장치·되돌리기·감사기록)** ✅
- **v3.2** 피어 도구(fail2ban·CrowdSec·GoAccess) 비교 후 적용: **Top 공격IP/경로 패널**(GoAccess) · **검색창·일시정지**(GoAccess/Kibana) · **임시·대역 차단·증거 저장** · **오탐 처리(신뢰 IP, fail2ban ignoreip·CrowdSec whitelist)** · **2단계 확인·실행 취소** ✅
  - 일부러 제외: 위협 인텔·지오로케이션·커뮤니티 차단목록(인터넷·외부 데이터 필요 → "오프라인·설치 0" 원칙과 충돌) · WebSocket(폴링으로 충분)
  - (선택) 자동 차단(규칙 기반 즉시 반응) · 클릭 시 LLM 상세 추천(키 있을 때만)은 향후

## 알려진 한계

실제 서버(INFOLINK 데모, ShotTrace)에 붙여 공격해보며 확인한 경계. 아는 것도 설계의 일부다.

- **제외 경로 DoS 사각지대** — `/health`·`favicon.ico` 등 정상 소음은 세지 않으므로, 그 경로로만 퍼붓는 폭주(DoS)는 보이지 않는다. 막으려면 정상 모니터링까지 오탐할 위험이 있어 일부러 두지 않았다. **대량 DoS 는 서버/프록시 계층(nginx rate limit 등)의 몫**이고, LogSentry 는 정찰·무차별·분산 탐지에 집중한다.
- **순수 과속 단독은 '관찰'** — 속도만 빠른 것은 정상 트래픽 급증과 구분이 어려워 경보 대신 관찰로 둔다(다른 신호와 겹치면 점수로 경보).
- **IP 분산** — 짧은 시간창에 뭉친 분산 무차별·스캔은 v2(P6)가 서버 전체 관점으로 잡는다. 다만 공격을 시간창보다 더 느리게 흩뜨리면(초저속 분산) 여전히 약하다 — 긴 창 집계·행동 패턴 묶음은 향후 과제.
- **계정 단위 신호** — 접근 로그 CLI 분석만으론 '대상 계정'을 못 본다. 앱에 `LoginTracker` 를 드롭인하면(v2 미들웨어) 비밀번호 스프레이·계정 집중을 계정 차원으로 잡는다.
- **상태코드가 비표준인 서버** — 어떤 서버는 로그인 실패를 401 이 아니라 **200**(서버 액션·GraphQL 등)으로, 없는 주소를 404 가 아니라 **307/302**(리다이렉트)로 응답한다(ShotTrace/Next.js 에서 확인). 그러면 상태코드에 기대는 인증 탐지(P2)·경로 탐색(P1)·분산 스캔이 무력해진다. **해결: ① 경로 기반 신호(탐침 경로 P4)는 상태코드와 무관하게 살아 있고, ② 로그인 성패는 상태코드 대신 `LoginTracker.record(..., success=앱이_판정)` 로 앱이 직접 넘기면 200 이든 307 이든 정확히 잡는다.** 상태코드만 믿지 말 것 — 이것이 로그 기반 분석의 본질적 한계다.
